## LLM04:2026 サプライチェーン

### 解説

LLM サプライチェーンは、学習データ、モデル、アダプタ、変換パイプライン、およびデプロイメント プラットフォームの完全性に影響を与える脆弱性の影響を受けやすく、結果として出力のバイアス、セキュリティ侵害、またはシステム障害が発生する可能性があります。従来のソフトウェアの脆弱性はコードの欠陥や依存関係に焦点を当てていましたが、機械学習においては、リスクはサードパーティ製の事前学習済みモデル、データセット、およびモデル アーティファクトにまで及び、これらは改ざん、汚染、または悪意のあるアーティファクトの置換によって操作される可能性があります。

LLM の作成は専門的な作業であり、LoRA などのパラメータ効率の高い微調整（PEFT）技術を用いて構築され、Hugging Face などのプラットフォームで共有されるサードパーティ製のモデル、データセット、および再利用可能なアダプタに依存しています。サプライチェーンには、モデル アーティファクト、出所、および変換/マージ ワークフローが第一級の攻撃対象領域として含まれており、デバイス上の LLM はこれをさらに拡大します。

ここで取り上げたリスクの一部は、LLM05:2026「データおよびモデルの汚染」でも議論されています。本書では、サプライチェーンの側面について重点的に解説します。エージェント型アプリケーション特有のサプライチェーンリスク（MCP サーバーやツール レジストリなど）については、OWASP Top 10 for Agentic Applications（OWASP GenAI Security Project、2026 年）の "ASI04: Agentic Supply Chain Vulnerabilities" で取り上げられており、MITRE ATLAS では、対応する攻撃手法が "AML.T0010: AI Supply Chain Compromise" （MITRE、n.d.）としてカタログ化されています。

これらのリスク領域は、[シンプルな LLM サプライチェーン脅威モデル](report/images/LLM%20Supply%20Chain%20Threat%20Model.png)で示されています。

### リスクの一般的な例

#### 1. 脆弱または古いサードパーティ コンポーネントとモデル

パッケージ、サービング フレームワーク、モデル自体など、古いまたは非推奨のコンポーネントは、LLM アプリケーションを侵害するために悪用される可能性があります。これは、[A06:2021 脆弱で古いコンポーネント](https://owasp.org/Top10/A06_2021-Vulnerable_and_Outdated_Components/) と同様ですが、モデル開発、微調整（ファイン チューニング）、または推論中にコンポーネントが使用される場合、リスクが高まります。LLM コーディング アシスタントは、新たな脆弱性をもたらします。大規模に、もっともらしいが実際には存在しないパッケージ名を生成するのです（Spracklen et al., 2025 年）。攻撃者は、これを事前に登録（「スロップ スクワッティング」）し、AI が提案する未検証の依存関係が悪意のあるコードに解決されるように仕向けます。

#### 2. ライセンス リスク

AI 開発には、使用、配布、商用化に関する様々な要件を課す多様なソフトウェアおよびデータセット ライセンスが伴います。これらを適切に管理しないと、法的およびコンプライアンス上のリスクが生じます。

#### 3. 脆弱または改ざんされた事前学習済みモデル

モデル アーティファクトを包括的に検査することは困難であり、静的解析だけでは動作上の安全性を確立することはできません。事前学習済みモデルには、汚染されたデータセットや直接的な改ざんによって導入された隠れたバイアスやバックドアが含まれている可能性があります。 Python の pickle など、ロード時に任意のコードを実行できる安全でないシリアライゼーション形式から移行することで、このリスクは軽減されますが、完全に排除されるわけではありません。バックドアはモデルの計算グラフに直接埋め込まれ、ONNX など広く安全とみなされている形式にも存在し続ける可能性があります。また、細工されたモデル ファイルは、llama.cpp の GGUF 解析におけるヒープ オーバーフロー（CVE-2024-23496）（Cisco Talos、2024 年）に見られるように、形式のネイティブ パーサーのメモリ破損バグを悪用する可能性があります。

#### 4. 脆弱な出所情報と署名のないモデル アーティファクト

公開されたモデルには、強力な出所保証がありません。モデル カードはモデルを文書化しますが、その出所を証明するものではありません。また、侵害された、あるいは偽装されたサプライヤー アカウントが、信頼できる名前で悪意のあるモデルを公開する可能性があります。モデル、アダプタ、データセット、微調整（ファイン チューニング）されたチェックポイント、および変換出力が署名またはハッシュ固定されていない場合、攻撃者は転送中、保存中、または自動化されたパイプラインがアーティファクトを信頼できる環境に受け入れるプロモーション境界において、アーティファクトを置き換えたり、密かに改ざんしたりする可能性があります。特に、パイプラインが不変のダイジェストではなく、可変の参照（例えば、`latest` タグ）でアーティファクトを解決する場合に、このリスクが高まります。

#### 5. 脆弱なアダプタと侵害された変換、マージ、および量子化ワークフロー

LoRA アダプタはファインチューニングをモジュール化して効率的にしますが、悪意のあるアダプタは、共同モデル マージ環境であろうと、デプロイされたモデルにアダプタをダウンロードして適用する推論プラットフォームであろうと、事前学習済みベースモデルの完全性を損なう可能性があります。モデル変換およびマージ サービスは、フォーマット間の変換中に悪意のある変更を導入し、レビューによる管理策を回避する可能性があります。量子化は関連する変換リスクです。モデルの重みを操作することで、完全精度モデルは正常に評価される一方で、量子化されたアーティファクトは攻撃者が選択した動作を示す可能性があります（Egashira et al., 2025 年）。そのため、完全精度モデルの保証は、デプロイされた量子化アーティファクトには引き継がれません。

#### 6. デバイス上の LLM のサプライチェーン脆弱性

デバイスに搭載される LLM は、製造プロセスの脆弱性、デバイスの OS またはファームウェアの脆弱性の悪用、改ざんされたモデルを含む再パッケージ化されたアプリケーションなどを攻撃対象に加えるため、デバイスの完全性とファームウェアの信頼性が LLM サプライチェーンの一部となります。

#### 7. 不明確な利用規約およびデータ プライバシー ポリシー

モデル事業者の利用規約（T&C）とデータ プライバシー ポリシーが不明確な場合、機密性の高いアプリケーション データがモデルの学習に使用されその後漏洩する可能性があり、モデル サプライヤーから提供された資材から著作権侵害のリスクが生じる可能性があります。

### 防止および軽減戦略

1. データ ソースとサプライヤーを、利用規約やプライバシー ポリシーを含め、慎重に審査し、信頼できるサプライヤーのみを使用します。サプライヤーのセキュリティとアクセス権限を定期的にレビューおよび監査し、セキュリティ態勢や利用規約の変更があった場合は再評価します。

2. OWASP Top Ten の [A06:2021 脆弱で古いコンポーネント](https://owasp.org/Top10/A06_2021-Vulnerable_and_Outdated_Components/) に記載されている対策を適用します。脆弱性スキャン、管理、およびコンポーネント、API、基盤となるモデルの保守されたバージョンをアプリケーションで維持するためのパッチ適用ポリシーを執行します。機密データにアクセスする開発環境にも同様の対策を適用し、AI が推奨する依存関係が存在すること、および意図したパッケージであることを、採用前に確認します。

3. サードパーティ モデルを選択する際には、対象となるユースケースに焦点を当て、AI レッド チーム演習と評価を実施します。また、実稼働環境では、MLOps および LLM パイプラインにおいて、異常検知と敵対的堅牢性テストを実施し、改ざんや汚染を検出します。

4. ソフトウェア部品表（SBOM）を用いて、最新の署名付きコンポーネント インベントリを維持します。このインベントリは、AI 部品表（AIBOM）および ML SBOM を用いて、モデル、アダプタ、データセットにも拡張します。OWASP CycloneDX ML-BOM（OWASP CycloneDX、n.d.）や OWASP AIBOM プロジェクト（OWASP GenAI Security Project、2025 年）などのオプションを検討します。ライセンスも同じインベントリで追跡し、コンプライアンスと透明性を確保するために定期的に監査します。

5. 検証可能なソースからのモデルのみを使用し、出所情報の不備は、サードパーティによる完全性チェック、署名、ファイル ハッシュで補います。透明性ログ（例えば、OpenSSF モデル署名プロジェクトや Sigstore）に裏付けられた暗号化モデル署名は、モデル アーティファクトを署名者のアイデンティティに紐付けます（Open Source Security Foundation、2025 年）。モデル学習において再現可能なビルドは保証されておらず、Coalition for Secure AI（CoSAI）は機械学習アーティファクトの署名に関する成熟度モデルを提供しています（OASIS Open、2025 年）。署名は完全性と出所を証明するものであり、安全性を証明するものではありません（侵害された、あるいは信頼できるものの悪意のある供給元からの有効な署名付きモデルであっても、バックドアが仕掛けられている可能性があります）。そのため、不変のアーティファクトの参照、出所ポリシー、ポリシー ベースのリリース ゲート（例えば、SLSA）（Open Source Security Foundation、n.d.）、動作評価、および上流モデルの完全性の継続的な検証と組み合わせる必要があります。同様に、外部から提供されるコードにはコード署名を使用します。

6. 共同モデル開発環境を厳密に監視および監査し、モデル変換およびマージ サービスを高リスクのプロモーション ポイントとして扱います。

7. エッジにデプロイされるモデルを完全性チェックとともに暗号化し、ベンダー認証 API を使用して改ざんされたアプリやモデルを防止し、認識されないファームウェアや信頼できないデバイス状態を拒否します。

### 攻撃シナリオの例

#### シナリオ #1: 侵害されたパッケージとサービング フレームワーク

侵害された依存関係がモデル開発環境または推論環境に到達するケースとして、2022 年 12 月に発生した PyTorch サプライチェーン攻撃が挙げられます。この攻撃では、PyPI レジストリ上の悪意のある `torchtriton` パッケージが正規の PyTorch-nightly 依存関係を偽装し、データを不正に流出させました（PyTorch Foundation、2022 年）。サービング スタックも同様の攻撃対象領域に含まれます。ShadowRay 攻撃では、問題となっているCVE-2023-48022（実稼働環境の Ray サーバー上の認証されていないダッシュボード）が実際に悪用され、その後、公開されたクラスター全体に自己増殖するボットネットへとエスカレートしました（Lumelsky & Elbaz、2025 年）。また、Ollama 攻撃では、CVE-2024-37032 が悪用され、レジストリから取得した悪意のあるモデルマニフェストを介してリモート コード実行が可能になりました（Wiz、2024 年）。


#### シナリオ #2: 改ざん済みモデルのハブへの公開

攻撃者は、信頼できると思われる名前で改ざんされたモデルを公開します。PoisonGPT の概念実証では、パラメータを意図的に改変したモデルが、標準的なベンチマーク評価による検出を回避しながら誤情報を拡散することが実証されています（Huynh & Hardouin、2023 年）。同様の信頼性のギャップは、攻撃者が人気モデルの安全機能を削除しつつ無害なタスクにおけるパフォーマンスを維持する微調整（Zhan et al.、2023 年）、検証なしにデプロイされたあらゆる事前学習済みモデル、そして研究者が悪意のあるモデルを介して推論コンテナから脱出し他の顧客のモデルやデータにアクセスする共有 AIaaS プラットフォームにも当てはまります（Tamari & Tzadik、2024 年）。

#### シナリオ #3: 侵害されたサプライヤー LoRA アダプタ

攻撃者はサードパーティのサプライヤーに侵入し、LoRA アダプタを巧妙に改変します。このアダプタは、モデルマージ ワークフローを通じてデプロイ済みの LLM にマージされます。マージ後、アダプタはシステムへの隠れた侵入経路となります。

#### シナリオ #4: 乗っ取られたモデル変換サービスまたはマージ サービス

攻撃者は、モデル マージ サービスまたはフォーマット変換サービスを介して攻撃を仕掛け、公開されているモデルを侵害し、悪意のある動作を注入します。これは、HiddenLayer が Hugging Face 上の Safetensors 変換ボットを乗っ取った事例（HiddenLayer、2024 年）で示されています。

#### シナリオ #5: モデル名前空間の再利用

組織は、公開ハブからモデルをデプロイする際に、`Author/ModelName` 識別子のみを使用してモデルを参照します。元の作成者がアカウントを削除または転送して名前空間を解放すると、攻撃者は同じ名前で再登録し、元のパスの下に悪意のあるモデルを公開します。名前だけでモデルを解決するパイプラインや管理モデル カタログは、攻撃者のモデルを取得し、リモート コード実行につながります（Saraf & Balassiano、2025 年）。

#### シナリオ #6: スキャナ、セーフ ローダー、セーフ フォーマットの迂回

ある組織は、サードパーティ モデルをマルウェア スキャナと、コード実行に対して安全であると文書化されたローダー オプションで保護しています。攻撃者はこれら両方を突破します。破損または圧縮された pickle ストリームは、スキャナが破損したバイトに到達する前にペイロードを実行します。これは、Hugging Face で発見された nullifAI モデル（Zanki、2025 年）に見られる脆弱性です。モデル スキャナとセーフ ローダー フラグには、PickleScan のゼロデイ脆弱性（Cohen、2025 年）や `torch.load` と `weights_only` の脆弱性（CVE-2025-32434）（GitHub Security Advisories、2025 年）など、迂回手法が CVE として割り当てられています。ONNX のような「安全な」フォーマットの計算グラフ（Wickens et al.、2024 年）に ShadowLogic スタイルのバックドアを仕掛けると、シリアライゼーション スキャナが検出できる実行可能コードが付加されません。スキャナーとセーフ ローダー フラグは、保証ではなく、出所検証やパッチ適用済みのローダーおよびパーサーと並ぶ多層防御レイヤーとして扱うべきです。

#### シナリオ #7: モデル アーティファクトのビルド パイプラインの侵害

攻撃者は、悪意のあるビルド ワークフローの依存関係、盗まれたアーティファクト レジストリの資格情報、またはキャッシュ汚染などを通じて、組織がモデルの微調整と公開に使用する CI/CD パイプラインを侵害します。Ultralytics 攻撃では、GitHub Actions のキャッシュ インジェクションにより、主要な AI ライブラリ（Python Package Index、2024 年）のトロイの木馬化された PyPI リリースが公開され、その中には侵害された「修正」リリースも含まれていました。これは、xz-utils バックドアや Codecov 侵害といった古典的なインシデントで見られるビルド時の置換と同じ手法です。バックドアが仕込まれたアーティファクトは、組織自身のリリース インフラストラクチャによってビルドおよび署名されるため、下流の出所チェック、内部認証、および外部ソース コンポーネントのみを検出するサプライチェーン スキャナーを通過してしまいます。


#### シナリオ #8: リバース エンジニアリングされたモバイル アプリ

攻撃者は、モバイル アプリをリバース エンジニアリングし、デバイス上のアプリを改ざんされたバージョンに置き換えます。この改ざんされたバージョンはユーザーを詐欺サイトに誘導し、ソーシャル エンジニアリングを通じて再パッケージ化されたアプリを拡散します。
