## LLM01:2026 プロンプト インジェクション

### 解説

**プロンプト インジェクション脆弱性**は、大規模言語モデル（LLM）への入力（ユーザーからの直接入力、取得した文書、ツール出力、画像/音声/動画コンテンツ、中間推論、永続メモリなど）が、アプリケーション開発者の意図しない方法でモデルの動作を変更した場合に発生します。LLM は「命令」と「データ」をアーキテクチャ的に区別しないため（どちらも同じストリーム上のトークンとして扱われます（NCSC、2025 年 12 月））、パラメータ化クエリに相当する明確な手段は存在しません。入力は人間が読める形式である必要はなく、ユーザーから直接送信される必要もなく、レンダリングされたインターフェースに表示される必要もありません。

プロンプト インジェクション脆弱性は、モデルが入力を処理する方法、およびその入力によってモデルがデータや命令をシステムの他の部分に誤って渡すように強制される方法に存在します。3 つのデプロイメント時特性が、この問題をさらに悪化させます。まず、**コンテキスト ウィンドウのプーリング**: モデルは、システム プロンプト、ユーザー入力、取得した文書、ツール出力、会話履歴、およびメモリを単一のトークン ストリームとして扱い、信頼境界を強制しません。次に、**メモリの永続性**: 長期メモリ、RAG コーパス、ベクトル ストア、またはホスト型メモリ サービスに書き込むインジェクションは、そのストアから読み取る後続のすべてのセッションを汚染します。最後に、**エージェント型の実行**: モデルの出力がツール呼び出し（ファイル システム、シェル、電子メール、クラウド API、MCP サーバー、サブ エージェントなど）を駆動する場合、影響範囲はチャット画面からエージェントのツールがアクセスできる範囲まで広がり、ツール出力はコンテキスト ウィンドウに再入力されるため、連鎖的または自己複製的な効果が可能になります。

プロンプト インジェクションの構造は、3 つの軸に沿って特徴付けることができます。**配信サーフェス**は、モデルに到達する方法（直接入力、取得コンテンツ、ツール出力、ツール接続チャネル、または永続メモリ）です。**伝播動作**は、時間と境界を越えて拡散する方法（シングル ショット、マルチ ステップ キル チェーン、メモリまたは RAG を介したセッション間、またはエージェント間での自己複製）です。**エンコーディング**は、悪意のある命令がトークンまたはピクセルでどのように表現されるか（平文、base64 またはその他の難読化、不可視 Unicode、マルチ モーダルまたはステガノグラフィ、低リソース言語）です。これらの軸に沿ってシナリオを分解することは、どの軽減策を適用するかを選択する前に、有用な脅威モデリング手順となります。

プロンプト インジェクションが成功した場合の深刻度と性質は、モデルが動作するビジネス コンテキストと、モデルが構築されている組織によって異なります。一般的に、プロンプト インジェクションは、以下のような結果をもたらす可能性があります（ただし、これらに限定されません）。

- 機密情報、システム プロンプトの内容、取得されたプライベート文書、またはインフラストラクチャの詳細の開示。
- モデルの出力を操作し、下流のシステムやユーザーが操作する偏った、有害な、または攻撃者が選択したコンテンツを生成。
- エージェントが呼び出しを許可されているツール（ファイル システム、シェル、メール、クラウド API）の不正な呼び出し。
- 画像 URL チャネル、レンダリングされた出力に隠された Unicode 文字、または秘密裏に行われるツール ログのサイド チャネルを介したデータ漏洩。
- メモリまたは RAG コーパスの汚染による、セッションをまたいだエージェント動作の永続的な侵害。

*注: プロンプト インジェクションは、モデルの出力（推論チャネルの内容を含みます）を通じて漏洩する情報を扱う LLM02:2025「機密情報の漏洩」や、モデルの出力が特権的なアクションに到達した場合の結果を扱う LLM06:2025「過剰な主体性」とは異なります。この項目は入力境界自体に関するものです。モデル出力が下流コンポーネントに到達する前の無害化と検証については、LLM10:2026「不適切な出力処理」で扱われます。*

### プロンプト インジェクションの種類

#### 直接プロンプト インジェクション

ユーザー、またはユーザーのアクセス パスを持つ攻撃者が、モデルの動作を意図しない方向に変更する入力を提供します。直接インジェクションは、**意図的**（悪意のあるユーザーがジェイル ブレイク（脱獄）を企てる場合）または**意図的でない**（正当なユーザーが、矛盾する指示を含むコンテンツをコピー＆ペーストした場合、または LLM を利用しているユーザーが、意図せず無関係な下流の LLM に対して入力を最適化した場合。詳細は、シナリオ #3 を参照）のいずれかです。

ジェイルブレイク（脱獄）は、攻撃者がモデルに安全性プロトコルを違反させることを目的とする、プロンプト インジェクションの一種です。アプリケーション レベルの安全性対策はジェイルブレイクの抑制に役立ちますが、効果的な防止には、モデルの学習と安全性機構の継続的な更新が必要です。

#### 間接プロンプト インジェクション

このモデルは、外部ソース（Web ページ、文書、メール、ツール応答、取得した RAG パッセージ、画像、MCP サーバーの出力、データベース行、issue のタイトルなど）から、プロンプト インジェクションとして機能するデータを含むコンテンツを取り込みます。ユーザーはこれらの指示を提供したり、閲覧したりしていません。配信領域の信頼プロファイル（分類基準の評価軸（a）（＝訳者注: 「セキュリティ対策を考える上での重要な指標」という意味合い））によって、どのような防御策が有効かが決まります。

- **信頼できない領域** 公開 Web ページ、送信者不明のメール、公開ファイル、検索結果。防御側は、これらのソースからのあらゆる情報を疑わしいものとして扱う必要があります。プロンプト インジェクションに関する研究のほとんどは、この領域に焦点を当てています。
- **ある程度信頼できる領域** 公開バグ トラッカーの issue のタイトル、パッケージの README ファイルと変更履歴、サード パーティ API の応答、ユーザーが取得を選択したが作成者ではないコンテンツ。ユーザーはプラットフォームを信頼していますが、個々の貢献者を必ずしも信頼しているわけではありません。
- **信頼できる領域** 開発者が所有するリポジトリ内のコード、開発者自身の運用データベースの行、社内文書、ユーザー自身のメールやカレンダー、同僚が作成したコンテンツなど。開発者は、攻撃者がここにコンテンツを配置したことに気づかない可能性があります。例えば、公開されているバグ報告フォームなど、無関係な上流の経路を介して攻撃が行われる場合もあります。

共有構造: 攻撃者はバックエンドを直接侵害する必要はありません。開発者の LLM が読み取る場所にテキストを配置し、開発者の権限で動作する LLM が処理を実行します。チャット インターフェースのみに焦点を当てた防御策では、この点を完全に無視してしまいます。

間接プロンプト インジェクションは、ユーザー自身の LLM インスタンスを、ユーザー自身のバックエンドに対する攻撃の武器として利用する手法として、ますます広く用いられています。攻撃パターンは、攻撃者が権限の低いチャネル（公開フォーム、カスタマー チケット、コミュニティのプル リクエストなど）を介して、ユーザーが信頼している場所にテキストを送信し、ユーザーの昇格された資格情報で動作しながら、ユーザーの MCP に接続されたエージェントまたは開発者アシスタントがそのテキストを読み取るのを待ちます。特権アクションを実行するのは、攻撃者ではなくエージェントです（一般的な例 #3 を参照。シナリオ #9 では、本番環境での概念実証について説明します）。

### リスクの一般的な例

1. **プロンプト入力の直接オーバーライド**: ユーザー メッセージがシステム プロンプトの役割と機能制限をオーバーライドし、モデルが本来のスコープ外で情報を開示、生成、または動作するようにします。意図的な入力と意図的でない入力の両方が対象となります。

2. **取得コンテンツを介した間接的なインジェクション**: 攻撃者の指示が RAG パッセージ、Web ページ、文書、または電子メールに埋め込まれ、コンテンツがコンテキスト ウィンドウに到達した際に実行されます（例: EmailGPT、INCIBE-CERT、2024）。

3. **信頼できるインターフェースを介した間接インジェクション**: 権限は低いものの信頼できるチャネル（issue 追跡システム、フィードバック フォーム、サポート チケットなど）に埋め込まれたテキストにより、ユーザーの LLM が自身の昇格された資格情報で動作し、リポジトリの漏洩、データベースのダンプ、または IDE 構成の変更など、攻撃者が直接実行できない操作を実行します（Invariant Labs、2025; General Analysis、2025; Rehberger、2025a）。

4. **マルチ モーダルおよびステガノグラフィによるインジェクション**: 画像、音声、または動画における知覚できないレベルの摂動がエンコーダによって抽出されます（Clusmann et al., 2025; シナリオ #6 を参照）。

5. **不可視文字の注入とデータの不正持出**: タグ ブロック、バリエーション セレクタ、およびゼロ幅 Unicode は、一見無害なテキストの中に命令を隠蔽したり、バイト データを流出させたりします。2024 年 8 月に発表された M365 Copilot の ASCII スマグリングの概念実証では、Slack の MFA コードが漏洩しました（Rehberger, 2024）。

6. **セッション間メモリおよび RAG コーパスの汚染**: 永続メモリまたは RAG コーパス内の汚染されたエントリが、それを読み込むすべての後続セッションに伝わります（W. Zou et al., 2025; シナリオ #4 を参照）。

7. **勾配オラクルとしての微調整インターフェース（「ファン チューニング」）**: 攻撃者は、ベンダーの微調整 API からサンプルごとの損失を読み取り、ペイロードを最適化します（Gemini に対する攻撃成功率は 65%～82%）。これにより、ホワイトボックス型の最適化がクローズド ウェイトモデルに導入されます（Labunets et al., 2025）。

8. **多言語、エンコード、または低リソース言語のペイロード**: 低リソースでコードが混在した入力は攻撃成功率を高め、このスキームで学習されていない分類器を回避します。また、Base64、ROT13、または絵文字エンコーディングは、エンコーディングを認識していないフィルタを迂回します（Hackett et al., 2025）。

### 防止および軽減戦略

プロンプト インジェクションは、現在の生成 AI に内在する脆弱性です。LLM は命令とデータをアーキテクチャ的に区別せず、その動作は確率的であるため、現時点では信頼できる防御機構は存在しません。これは、NIST（2025）、NCSC（2025）、および Debenedetti ら（2025）の見解と一致しています。従って、防御は傍受型ではなく、アーキテクチャ的なアプローチが求められます。モデルの命令境界が最終的に迂回されることを前提として周辺システムを設計し、モデルに許可される動作と出力の到達範囲を制限することで、インジェクションの成功がエクスプロイトの成功に直結しないようにする必要があります。

記録されている重大なプロンプト インジェクション事件のほとんどは、インジェクションが、ツール、スコープ、または出力レンダリング機能によって、侵害されたモデルが攻撃者の代理としてユーザーの権限レベルで動作することを許容するシステム内部に侵入したために深刻な事態に至りました（シナリオ #7～#9 を参照）。この項目と **LLM03:2026 過剰な主体性**との間の運用上の関係は次のとおりです。入力側の侵害はプロンプト インジェクションであり、過剰な機能、権限、または自律性によって、その侵害がチャット ウィンドウ外にも影響を及ぼすことになります。サイモン・ウィリソンの「致命的な三要素」（2025）は、デプロイメント前のチェックとして同じ構造診断を改めて示しています。プライベート データへのアクセス、信頼できないコンテンツの取り込み、外部との通信を同時に行えるエージェントは、重大な影響を及ぼすエクスプロイトを行う条件を備えており、いずれか 1 つを取り除けば、その条件は満たされます。

単一の管理策では不十分なため、以下の管理策を多層防御として適用してください。一部の管理策はインジェクションの成功率を低下させますが、適応型攻撃者に対しては効果が薄れることが予想されます。他の管理策は、インジェクションが成功した場合の被害範囲を制限し、システムを調査できる攻撃者に対しては有効です。エージェント型のデプロイメントの場合、最小権限および機能割り当ての対策（#4、#8）が主要な役割を担っており、**LLM03:2026** にはエージェント側での対応策が網羅されています。

1. **システム プロンプトでモデルの役割と機能を制限します**。無制限の権限付与ではなく、宣言的な許可/拒否ステートメント（「X のみを支援する、Y にはアクセスしない、外部アドレスに出力を転送しない」など）を使用してください。これは部分的な管理策に過ぎません。プロンプトを推測した攻撃者はこれを回避できます（Nasr et al., 2025）。そのため、4 番目の特権制御と組み合わせて使用してください。

2. 下流システムが処理を実行する前に、**厳密な出力スキーマを定義し、信頼できるアプリケーション コードですべての応答を検証します**。2 番目の LLM 呼び出しではなく、構造検証を使用してください。これにより、セマンティック操作ではなく、フォーマット違反を検出できます。スキーマが有効な応答であっても、悪意のある SQL クエリやデータ漏洩を目的としたメール本文が含まれている可能性があります。

3. **テキストだけでなく、すべてのモダリティ境界（テキスト、画像、音声、構造化データ）でフィルタリングします**。モダリティ固有の分類器、画像に対する OCR、音声に対する文字起こしを実行し、抽出されたコンテンツにテキスト フィルタを適用してください。セマンティック フィルタは言い換えやエンコードによって回避可能であり、リソースの少ない入力やコードが混在した入力は精度を低下させます（Hackett et al., 2025）。

4. **資格情報と状態変更機能は、モデルではなくアプリケーション コードに保持し、操作ごとに最小権限のみを付与します**。特権呼び出しは、実行時に意図と引数を再検証する決定論的なポリシー エンジンを通してルーティングします。NIST AI 100-2 E2025 および CISA と Five Eyes OT の共同ガイダンス（CISA et al., 2025）は、この決定論的な仲介を調達における基本要件として位置付けています。広範な「利便性」のための権限やマルチ エージェント ホップは、下流でリスクを再導入します。

5. **取り込みとレンダリングの境界ごとに、タグ ブロック（U+E0000～E007F）、バリエーション セレクタ（U+FE00～FE0F）、およびゼロ幅文字（U+200B、U+200C、U+200D、U+2060）を削除します。** これらは通常のレンダリングでは見えず、命令やデータ漏洩バイトを密かに送り込みます（一般的な例 #5 を参照）。また、バリエーション セレクタのバリアント（Rehberger、2025c）は、任意のバイトを不可視に送り込みます。除去（ストリッピング）は、可視テキスト ペイロードや将来のステガノグラフィクラスを阻止するものではありません。

6. **外部コンテンツを構造的に分離された、出所ラベル付きチャネルを通して渡す**ことで、モデルがデータと命令を区別できるようにします（S. Chen et al.、2025; Microsoft Research、2025）。これは非適応型テストでの攻撃成功率を低下させるだけであり、マーキング方式を知っている攻撃者はそれを模倣することができ、StruQ （※訳者注: "Structured Query" のこと）は適応型攻撃で回避されました（Nasr et al., 2025）。

7. **特権的な操作、取り消し不可能な操作、または外部から見える操作を行う前に、必ず人間の明確な承認を要求します**。承認者には、要約ではなく、実行された操作を正確に表示してください。目に見えない文字の不正挿入によって、表示される操作と実際に実行された操作が異なる可能性があります（#5）。また、承認作業の負担が大きくなると、承認者の判断力が低下します。

8. **Rule of Two を最低ラインとしてエージェントの権限を配分（budget）します**（Meta AI、2025 年）。(A) 信頼できない入力、(B) 機密データ、(C) 状態変更または外部通信への同時アクセス は高リスクとみなしてください。[A、B、C] のいずれのエージェントも、操作ごとに人間の承認が必要であり、[A、B] または [A、C] の構成では、明確な残留リスク評価が必要です（シナリオ #8 を参照）。 NIST AI 100-2 E2025 および CISA、FBI、NSA、ACSC の OTガイダンス（CISA 他、2025）は、自律性の深度については言及していないものの、このルールを支持しています（Noma Security、2025）。

9. **エージェントのメモリ書き込みを特権操作として扱います**。書き込みの原因となったプロンプトをログに記録し、書き込みを命令またはロール変更の内容に基づいて分類し、命令を含むメモリがセッション間で保持される前に承認を要求します。2025年 2 月のGemini PoC（Rehberger、2025b）では、ツールの呼び出しを遅延させることでメモリを汚染しました（MITRE、n.d.）。事実のエントリは命令に紛れ込みやすく、増分書き込みは書き込みごとの分類を回避できる可能性があります。

10. **すべての MCP サーバーとサードパーティ ツール パッケージをピン留め、署名、検証し、ツールの説明を監査して隠された命令を検出し、ツールの構成を監視します**。これらをソフトウェア サプライチェーンのサーフェスとして扱い、サードパーティ ツール パッケージについては **LLM04:2026 サプライチェーン**、MCP サーバーとツール レジストリについては ASI04 エージェント サプライチェーンの脆弱性（シナリオ #9 を参照）でカバーします。ピン留めは、ピン留めされたバージョンで出荷されるペイロードや、バージョンを変更しないツールの説明の改ざんを防ぐものではありません。

11. **デプロイ済みの防御策を読み込んだ適応型攻撃者に対してテストを行い、静的攻撃のみの成功主張を拒否します**。AgentDojo（Debenedetti et al., 2024）と JailbreakBench（Chao et al., 2024）でベースラインを設定し、その後、完全な防御仕様をテスターに開示してレッド チーム テストを実施します。Nasr et al. （2025）は、最近の 12 の防御策のほとんどで静的攻撃の成功率はほぼゼロである一方、適応型攻撃の成功率は 90% を超えていることを発見しました（LLMail-Inject、Microsoft Security Response Center、2025 も参照）。

### 攻撃シナリオの例

#### シナリオ #1: 直接インジェクション

攻撃者は、カスタマー サポート チャットボットにガイドラインを無視させ、プライベート データ ストアへのクエリ実行やメール送信を行わせ、不正アクセスと権限昇格を招きます。

**構成要素:** (a) ユーザーによる直接入力、(b) シングル ショット、(c) 平文

#### シナリオ #2: 取得した Web コンテンツを介した間接インジェクション

ユーザーがアシスタントに、隠された指示を含む Web ページの要約を依頼します。モデルは、プライベートな会話内容を攻撃者が管理するドメインに流出させる URL を持つ Markdown 画像を挿入します。ユーザーはレンダリングされた画像のみを目にし、指示内容は一切表示されません。

**構成要素:** (a) 取得した Web コンテンツ（間接的）、(b) 画像 URL による流出を伴うシングル ショット、(c) ページソースに隠された平文

#### シナリオ #3: 意図的ではないインジェクション

求人情報 PDF に、AI 検出指示が埋め込まれています。応募者が知らず知らずのうちに LLM を使って履歴書を最適化しようとすると、モデルがその指示を検知し、採用システムがその候補者をフラグ付けします。これは、どちらの当事者も悪意を持って行動していないにもかかわらず、即座にインジェクションが発生するケースです。

**構成要素:** (a) 間接（文書／PDF）、(b) 単発的、(c) 平文

#### シナリオ #4: RAG リポジトリの汚染

攻撃者は、アプリケーションが取得するコーパスに、改ざんされた文書を追加します。一致するクエリは改変されたコンテンツを返し、その指示によって出力が変更されます。わずか 5 つの改ざんされた文書で、数百万のテキストからなる知識ベースに対して約 90% の攻撃成功率を達成した事例があります（W. Zou et al., 2025）。

**構成要素:** (a) 取得コンテンツ（RAG コーパス）、(b) セッション間／ユーザー間、(c) 平文

#### シナリオ #5: ペイロード分割

攻撃者は、悪意のある命令を複数の履歴書フィールド（ヘッダー、本文、添付ファイル）に分割します。これにより、フィールドごとの分類器では、どのフィールドも悪意のあるものとは認識されません。LLM は評価時にこれらの命令を再結合し、その結果、推奨結果が操作されます。

**構成要素:** (a) フィールドをまたいで分割された直接ユーザー入力、(b) 評価時に再結合されたシングル ショット、(c) 断片化された平文

#### シナリオ #6: マルチ モーダル ステガノグラフィ インジェクション

攻撃者は、人間の視覚閾値以下の画像に命令を埋め込みます。マルチ モーダル モデルのビジョン エンコーダーがペイロードを抽出すると、動作が変化し、モデルは有害な出力、または不正なツール呼び出しを生成します。これは、腫瘍画像における 4 つの最先端のビジョン言語モデル（Clusmann et al., 2025）と、視覚的摂動とテキスト操作を組み合わせた汎用モデル（R. Chen et al., 2025）に対して実証されました。

**構成要素:** (a) 画像入力（間接／マルチ モーダル）、(b) シングル ショット、(c) ステガノグラフィ／ピクセル レベル エンコーディング

#### シナリオ #7: ゼロ クリック文書経由のエージェント型データの不正持出

細工されたメールが、LLM を利用した生産性向上アシスタントをトリガーし、ユーザーの操作なしに組織データを不正に持出します。Aim Security は、Microsoft 365 Copilot（Reddy & Gujral、2025）に対してこの攻撃を実証し、導入済みのプロンプト インジェクション分類器とリンク削除フィルタの両方を回避しました。

**構成要素:** (a) メール／文書（間接的）、(b) ツール呼び出しによるシングル ショット、(c) 目に見えない Unicode データ不正持出しチャネルを用いた平文

#### シナリオ #8: エージェント型破壊コマンド実行

2025 年 7 月に発生した 2 つの事例は、異なる経路で同じ種類の被害をもたらしました。攻撃者は、AWS がロールバックする前に、Amazon Q VS Code 拡張機能リポジトリに破壊的なシステム プロンプトをコミットしましたが、コミットされたコードは構文エラーのため実行されませんでした（Amazon Web Services、2025a）。また、別のランタイム インジェクションにより、Amazon Q で任意のコードが実行されました（Amazon Web Services、2025b）。シェル、ファイル システム、またはクラウド API へのアクセス権を持つエージェントは、ホストに影響を与えるインシデントへのインジェクションを増幅させます。

**構成要素:** (a) サプライチェーン/侵害されたシステム プロンプト、またはランタイム間接インジェクション、(b) セッション間永続インジェクション、またはシェル ツール実行による単発インジェクション、(c) 平文

#### シナリオ #9: MCP を介した信頼済みバックエンド間接インジェクション

攻撃者は、権限の低いチャネル（公開されている GitHub issue、サポートチケット、または悪意のある npm パッケージ）にテキストを埋め込み、開発者の LLM が昇格された資格情報でそれを読み取ります。 Invariant Labs（2025 年）は、改ざんされた GitHub issue を介してプライベート リポジトリを流出させ、General Analysis（2025 年）は、`service_role` を実行し行レベル セキュリティを回避した Cursor の Supabase MCP サーバーを介して本番データベースをダンプし、悪意のある `postmark-mcp` パッケージ（Koi Security、2025 年；Toulas、2025 年）は、推定 300 の組織にまたがる攻撃者へのメールを BCC で送信しました。

**構成要素:** (a) 信頼できるサーフェスを介した間接的な攻撃（MCP チャネル: issue、チケット、npm パッケージ）、(b) 複数ステップのツール チェーン、(c) 平文
