## LLM03:2026 過剰な主体性

### 解説

LLM ベースのシステムは、開発者によって一定の権限を与えられることがよくあります。これは、プロンプトに応じてアクションを実行するために、ツール（ベンダーによっては拡張機能、プラグイン、スキルなどと呼ばれることもあります）を介して関数を呼び出したり、他のシステムとインターフェースしたりする機能です。LLM エージェントは、入力プロンプトまたは以前の LLM 出力に基づいて、呼び出すツールを動的に選択することもできます。エージェント ベースのシステムは通常、以前の呼び出しの出力を使用して、後続の呼び出しを検証および指示するために、LLM への呼び出しを繰り返し行います。

過剰な主体性とは、LLM の誤動作の原因に関係なく、LLM からの予期しない、曖昧な、または操作された出力に応じて、有害なアクションを実行できる脆弱性です。一般的なトリガーには、以下のようなものがあります。

- 設計が不十分な無害なプロンプト、あるいは単にパフォーマンスの低い/整合性（アライメント）の取れていないモデルによって引き起こされる幻覚/虚言。
- 悪意のあるユーザーによる直接/間接プロンプト インジェクション、悪意のある/侵害されたツールの以前の呼び出し、または（マルチ エージェント/協調システムの場合）悪意のある/侵害されたピア エージェント。

過剰な主体性の根本原因は、通常、以下のいずれか、または複数です。

- 過剰な機能
- 過剰な権限
- 過剰な自律性

過剰な主体性は、機密性、完全性、可用性のスペクトル全体にわたって広範な影響を及ぼす可能性があり、LLM ベースのアプリケーションがどのシステムと相互作用できるかに依存します。エージェント型システムのコンテキストでは、過剰な主体性は、「ASI02: ツールの不正使用と悪用」、「ASI03: アイデンティティと権限の乱用」、「ASI08: 連鎖的な障害」として現れる可能性があります。

注: 過剰な主体性は、LLM 出力の不十分な精査に関する不適切な出力処理とは異なります。モデルの入力と出力の無害化は、過剰な主体性の根本対策ではなく、入力については「LLM01: 2026 プロンプト インジェクション」、出力については「LLM10:2026 不適切な出力処理」で規定されています。

### リスクの一般的な例

#### 1. 過剰な機能

LLM エージェントは、システムの本来の動作に必要のない機能を含むツールにアクセスできます。例えば、開発者は LLM エージェントにリポジトリから文書を読み取る権限を与える必要がありますが、選択したサードパーティ製ツールには文書の変更や削除の権限も含まれています。

#### 2. 過剰な機能

開発段階で試用されたツールが、より優れた代替ツールに置き換えられた場合でも、元のツールが LLM エージェントからアクセス可能な状態のままになっていることがあります。

#### 3. 過剰な機能

機能が無制限な LLM ツールは、アプリケーションの本来の動作に必要な範囲外のコマンドに対する入力指示を適切にフィルタリングできません。例えば、特定のシェル コマンドを実行するツールが、他のシェル コマンドの実行を適切に防止できない場合があります。

#### 4. 過剰な権限

LLM ツールは、下流システムに対してアプリケーションの本来の動作に必要のない権限を持っています。例えば、データ読み取りを目的としたツールが、SELECT 権限だけでなく UPDATE、INSERT、DELETE 権限も持つアイデンティティを使用してデータベース サーバーに接続する場合が挙げられます。

#### 5. 過剰な権限

個々のユーザーのコンテキストで操作を実行するように設計された LLM ツールが、汎用的な高権限アイデンティティを使用して下流システムにアクセスしています。例えば、現在のユーザーの文書ストアを読み取るツールが、すべてのユーザーのファイルへのアクセス権を持つ特権アカウントを使用して文書リポジトリに接続する場合が挙げられます。

#### 6. 過剰な自律性

LLM ベースのアプリケーションまたはツールが、影響の大きい操作を独立して検証および承認していません。例えば、ユーザーの文書を削除できるツールが、ユーザーの確認なしに削除を実行する場合が挙げられます。

## 防止および軽減戦略

過剰な主体性を防止するには、以下の対策が有効です。

#### 1. ツールの最小化

LLM エージェントが呼び出せるツールは、必要最低限のものに限定します。例えば、LLM ベースのシステムが URL の内容を取得する機能を必要としない場合、そのようなツールは LLMエ ージェントに提供すべきではありません。

#### 2. ツールの機能の最小化

LLM ツールに実装する機能は、必要最低限のものに限定します。例えば、ユーザーのメール ボックスにアクセスしてメールを要約するツールは、メールの読み取り機能のみを必要とする場合があるため、メッセージの削除や送信などの機能は含めるべきではありません。

#### 3. 汎用的なツールの回避

可能な限り汎用的なツール（シェル コマンドの実行、URL の取得など）の使用を避け、よりきめ細かな機能を持つツールを使用します。例えば、LLM ベースのアプリケーションは、出力をファイルに書き込む必要がある場合があります。シェル関数を実行するツールを使ってこれを実装した場合、望ましくない操作が行われる範囲が非常に広くなります（他のシェル コマンドも実行できてしまうため）。よりセキュアな代替策としては、その特定の機能のみを実装する専用のファイル書き込みツールを作成することです。ツールは、入力パラメータに対して厳密なスキーマを定義し、使用前に内容を検証する必要があります。

#### 4. ツールの権限の最小化

LLM ツールが他のシステムに付与する権限は、望ましくない操作の範囲を制限するために必要最小限に抑えるべきです。例えば、顧客に購入推奨を行うために製品データベースを使用する LLM エージェントは、「products」テーブルへの読み取りアクセスのみを必要とする場合があります。他のテーブルへのアクセス権や、レコードの挿入、更新、削除を行う権限は持つべきではありません。これは、LLM ツールがデータベースに接続するために使用するアイデンティティに対して適切なデータベース権限を適用することで実現する必要があります。

#### 5. ユーザーのコンテキストでのツールの実行

ユーザーの認証とセキュリティ スコープを追跡し、ユーザーに代わって実行されるアクションが、下流システム上でその特定のユーザーのコンテキストで、かつ必要最小限の権限で実行されるようにします。例えば、ユーザーのコード リポジトリを読み取る LLM ツールは、ユーザーに OAuth による認証と必要最小限のスコープを要求する必要があります。委任ワークフローやマルチ エージェント ワークフローでは、呼び出し元のエージェントまたはサービスのアイデンティティの権限のみに依存するのではなく、連鎖するツールやエージェント呼び出し全体にわたって、元のユーザー コンテキストと認証スコープを維持します。

#### 6. ユーザー承認の必須化

ヒューマン イン ザ ループの管理作を用いて、影響の大きいアクションを実行する前に人間の承認を必須とします。これは、下流システム（LLM アプリケーションの範囲外）または LLM ツール自体に実装できます。例えば、ユーザーに代わってソーシャル メディア コンテンツを作成・投稿する LLM ベースのアプリケーションは、「投稿」操作を実行するツール内にユーザー承認ルーチンを含めるべきです。

#### 7. 完全な仲介

アクションの許可・不許可を LLM に委ねるのではなく、ロジックに基づいて認可を実装します。完全な仲介の原則を適用し、下流システムへのすべてのリクエストが、ツール、ツールと下流システム間の独立した実行前ポリシー決定ポイント、または下流システム自体によってセキュリティ ポリシーに照らして検証されるようにします。このようなポリシーは、エージェントの名目上許可されたアクションが状況によっては安全でない場合に対処するのに役立ちます。段階的な執行ポリシー（監査、警告、ブロック、エスカレーション）により、影響の少ない、または容易に取り消し可能なアクションは自動承認され、影響の大きい、または取り消し不可能なアクションは人間のレビューに回されます。例えば、カスタマー サービス チャットボットは、返金をストア クレジット（回収可能）として自動処理できますが、外部への支払いなどの取り消し不可能なアクションは人間の承認に回されます。

以下のオプションは、過剰な主体性を完全に防止するものではありませんが、発生する損害のレベルを制限することができます。

#### 8. ツールの使用状況の監視

LLM ツールおよび下流システムの活動をログに記録し、監視することで、望ましくないアクションが発生している箇所を特定し、適切に対応します。

#### 9. レート制限の実施

ツールの呼び出しに関するしきい値を設定し、そのしきい値を超えた場合に停止、レート制限、または人間のレビューへのエスカレーションを行うサーキット ブレーカーを実装します。単純なしきい値は呼び出し回数に基づいて設定できますが、コンテキストを考慮したしきい値は、ツールへの入力パラメータの累積値に基づいて設定できます。

### 攻撃シナリオの例

#### シナリオ #1: メール アシスタントの乗っ取り

LLM ベースのパーソナル アシスタント アプリは、受信メールの内容を要約するために、ツールを介して個人のメール ボックスへのアクセス権を取得します。この機能を実現するには、ツールはメッセージを読み取る必要がありますが、システム開発者が選択したツールにはメッセージ送信機能も含まれています。このアプリは、間接プロンプト インジェクション攻撃に対しても脆弱です。この攻撃では、悪意を持って作成された受信メールが LLM を騙し、エージェントにユーザーの受信トレイをスキャンして機密情報を探し出し、攻撃者のメール アドレスに転送するように指示します。これは以下の方法で回避できます。

- メール読み取り機能のみを備えたツールを使用することで、過剰な機能を排除します。
- 読み取り専用スコープの OAuth セッションを介してユーザーのメール サービスに認証することで、過剰な権限を排除します。
- LLM ツールで作成されたすべてのメールについて、ユーザーが手動で内容を確認し、「送信」ボタンをクリックするようにすることで、過剰な自律性を排除します。

あるいは、メール送信インターフェースにレート制限を実装することで、被害を軽減することも可能です。
