## LLM10:2026 不適切な出力処理

### 解説

不適切な出力処理とは、大規模言語モデル（LLM）によって生成された出力が、他のコンポーネントやシステムに渡される前に、出力の検証・無害化・処理が不十分な状態を指します。LLM によって生成されたコンテンツはプロンプト入力によって制御できるため、この動作はユーザーに間接的に追加機能へのアクセスを提供するのと類似しています。

不適切な出力処理は、モデル出力が下流に渡される前に安全でない方法で使用されることに関するものであり、「LLM07:2026 誤情報」とは不正確または誤解を招く出力に関する点で異なります。モデル入力の検証と無害化は、「LLM01:2026 プロンプト インジェクション」でカバーされています。

不適切な出力処理の脆弱性が悪用されると、Web ブラウザにおける XSS および CSRF 攻撃、バックエンド システムにおける SSRF 攻撃、権限昇格、またはリモート コード実行が発生する可能性があります。

以下の条件は、この脆弱性の影響を増大させる可能性があります。

- LLM に過剰なアプリケーション権限が付与され、権限昇格またはリモート コード実行が可能になっている場合。

- 間接プロンプト インジェクションに対する脆弱性があり、攻撃者がターゲット ユーザーの環境への特権アクセスを取得できる可能性がある場合。

- サードパーティ ツールからの入力が検証されていない場合。

- コンテキスト固有の出力エンコーディング（HTML、JavaScript、SQLなど）が欠落している場合。

- LLM 出力の監視とログ記録が不十分である場合。

- LLM 使用時のレート制限または異常検知が欠落している場合。

- ANS Iエスケープ シーケンスなどの制御文字を無効化せずにモデル出力をレンダリングするターミナル、ログ、または IDE のシンクが存在する場合。

- モデル出力で参照される外部リソース（Markdown 画像、リンク プレビュー、iframe など）を自動的に取得するクライアント レンダラー（ブラウザ、チャット UI、IDE、ターミナル）が存在し、送信リクエストを通じてコンテキスト データが漏洩する可能性がある場合。

### リスクの一般的な例

1. LLM の出力がシステム シェルや exec、eval などの類似関数に直接入力されると、リモート コード実行が発生します。

2. LLM によって JavaScript または Markdown が生成され、ユーザーに返されます。生成されたコードはブラウザで解釈され、XSS 攻撃が発生します。

3. LLM で生成された SQL クエリが適切なパラメータ化なしに実行されると、SQL インジェクション攻撃が発生します。

4. LLM の出力が適切な無害化処理なしにファイル パスの構築に使用されると、パス トラバーサル攻撃の脆弱性が発生する可能性があります。

5. LLM で生成されたコンテンツが適切なエスケープ処理なしにメール テンプレートに使用されると、フィッシング攻撃につながる可能性があります。

6. ANSI エスケープ シーケンスやその他の制御文字を含む LLM の出力が、それらを解釈する端末、ログ ビューア、または IDE ペインに書き込まれると、ビジュアル スプーフィング、クリップボード ハイジャック（例えば、OSC 52）、または既知の端末エミュレータの脆弱性の悪用（Rehberger、2024b）が可能になります。

7. チャット UI は、モデル出力で参照される Markdown 画像またはリンク プレビューを自動的にレンダリングするため、モデル コンテキストの一部を制御する攻撃者は、画像 URL のホスト名またはクエリ文字列を介して会話データを抜き取ることができます（Rehberger、2024a）。

### 防止および軽減戦略

1. モデルを他のユーザーと同様に扱い、ゼロ トラストのアプローチを採用し、モデルからバックエンド関数への応答に対して適切な入力検証を適用します。

2. 効果的な入力検証と無害化を確保するため、OWASP ASVS（アプリケーション セキュリティ検証標準）ガイドラインに従います（OWASP、n.d.）。

3. JavaScript や Markdown による意図しないコード実行を軽減するため、モデルの出力をエンコードしてユーザーに返します。OWASP ASVS は出力エンコーディングに関する詳細なガイダンスを提供しています。

4. LLM 出力の使用場所に基づいて、コンテキストに応じた出力エンコーディングを実装します（例: Web コンテンツの場合は HTML エンコーディング、ブラウザ スクリプト コンテキストの場合は JavaScript エンコーディング）。

5. LLM 出力を含むすべてのデータベース操作には、パラメータ化クエリまたはプリペアド ステートメントを使用します。

6. LLM 生成コンテンツからの XSS 攻撃のリスクを軽減するため、厳格なコンテンツ セキュリティ ポリシー（CSP）を適用します。

7. 悪用試行を示唆する可能性のある LLM 出力の異常なパターンを検出するために、ログ記録および監視システムを実装します。

8. モデル出力を端末、ログ ファイル、またはその他の解釈対象に書き込む前に、制御文字（ANSI エスケープ シーケンス、BEL、OSC、バック スペース、キャリッジ リターン）およびその他の印刷不可能なバイトを無害化します。保持する必要がある場合は、それらを視覚的にエンコードします。

9. クライアント レンダラー（チャット UI、IDE、メール クライアント、モバイル アプリ）では、モデル出力が攻撃者が制御するエンドポイントへの自動送信リクエストをトリガーしないようにします。Markdown 画像、リンク プレビュー、iframe、および類似の要素の自動レンダリングはデフォルトで無効にします。レンダリングが必要な場合は、フェッチを明示的な許可リストのオリジンに制限するか、データを含むクエリ パラメータを削除するサーバー サイド フェッチャーを介してプロキシします。

### 攻撃シナリオの例

#### シナリオ #1

あるアプリケーションは、チャットボット機能の応答を生成するために LLM ツールを使用しています。このツールは、別の特権 LLM がアクセスできる複数の管理機能も提供しています。汎用 LLM は、適切な出力検証を行わずに応答をツールに直接渡してしまうため、ツールはメンテナンスのためにシャットダウンしてしまいます。

#### シナリオ #2

あるユーザーは、LLM を搭載したウェブサイト要約ツールを使用して記事の簡潔な要約を生成します。このウェブ サイトには、LLM にウェブ サイトまたはユーザーの会話から機密情報を取得するよう指示するプロンプトが埋め込まれています。LLM は、取得した機密データをエンコードし、出力検証やフィルタリングを行わずに、攻撃者が制御するサーバーに送信します。

#### シナリオ #3

LLM は、チャットのような機能を通じて、ユーザーがバックエンド データベースに対して SQL クエリを作成できるようにします。ユーザーがすべてのデータベース テーブルを削除するクエリを要求します。LLM によって作成されたクエリが検証されない場合、すべてのデータベース テーブルが削除されてしまいます。 

#### シナリオ #4

Web アプリケーションが、出力の無害化を行わずに、ユーザーのテキスト プロンプトからコンテンツを生成するために LLM を使用しています。攻撃者は、細工されたプロンプトを送信することで、LLM が無害化されていない JavaScript ペイロードを返し、被害者のブラウザでレンダリングされた際に XSS 攻撃を引き起こす可能性があります。この攻撃は、モデル出力の検証とエンコードが不十分であったために発生しました。

#### シナリオ #5

マーケティング キャンペーン用の動的なメール テンプレートを生成するために LLM が使用されています。攻撃者は、メール コンテンツに悪意のある JavaScript を組み込むように LLM を操作します。アプリケーションが LLM 出力を適切に無害化していない場合、脆弱なメール クライアントでメールを閲覧する受信者に対して XSS 攻撃が発生する可能性があります。

#### シナリオ #6

アプリケーションが、人間のレビューやセキュリティ テストを行わずに、LLM で生成されたコードを自動的にコンパイルしてデプロイしています。出力が信頼され、検証なしで実行されるため、安全でないコードが実稼働環境にデプロイされ、悪用される可能性があります。
